# N+1 개선, 쿼리 수와 응답 시간

문제집 목록과 주간 통계가 지연 로딩과 메모리 필터 때문에 내던 추가 쿼리를 없앴다.
이 문서는 그 개선을 쿼리 수와 응답 시간 두 가지로 확인한 기록이다.

## 1. 무엇을 어디서 재나

| 지표 | 테스트 | DB | 왜 |
|---|---|---|---|
| 쿼리 수 | `WorkBookListQueryCountTest`, `StatisticsQueryCountTest` | H2 인메모리 | 어디서 재든 같은 값이라 빠른 쪽에서 잰다 |
| 응답 시간 | `N1LatencyBenchmarkTest` | MySQL 8.0 (도커) | H2 는 라운드트립이 없어 개선 폭이 실제보다 작게 나온다 |

쿼리 수는 Hibernate 통계의 prepared statement 수다. 실제로 DB 에 나간 SQL 개수를 센다.

## 2. 응답 시간 측정 방법

```bash
export BENCH_MYSQL_PASSWORD=아무거나
docker run -d --name nq-bench-mysql \
  -e MYSQL_ROOT_PASSWORD="$BENCH_MYSQL_PASSWORD" -e MYSQL_DATABASE=nq_bench \
  -p 3309:3306 mysql:8.0

./gradlew test --tests "*N1LatencyBenchmarkTest" -Dspring.profiles.active=mysql
```

시나리오마다 개선 전과 개선 후를 번갈아 돌린다. 워밍업 2회로 InnoDB 버퍼 풀과 JIT 를 데운 뒤
5회를 재고 p50 을 남긴다. 회차마다 영속성 컨텍스트를 비워 1차 캐시가 섞이지 않게 하고,
두 경로가 같은 값을 돌려주는지도 매번 확인한다. 빨라졌지만 결과가 다르면 의미가 없다.

`mysql` 프로파일 없이 돌리면 테스트가 스스로 건너뛴다. H2 로 떨어진 시간을 실측으로
착각하지 않기 위해서다.

## 3. 결과

MySQL 8.0.46, 도커 컨테이너, 로컬 루프백 기준.

| 화면 | 쿼리 (전 → 후) | p50 (전 → 후) | p95 (전 → 후) |
|---|---|---|---|
| 문제집 목록, 10개 각 20문제 | 211 → 2 | 117.0ms → 2.2ms | 153.0ms → 3.2ms |
| 문제집 목록, 50개 각 100문제 | 5,051 → 2 | 10.09s → 12.2ms | 10.82s → 13.5ms |
| 주간 통계, 6개월치 기록 | 22 → 1 | 20.4ms → 2.4ms | 21.9ms → 3.4ms |

문제집 50개 기준으로 쿼리는 2,526배, 응답 시간은 825배 줄었다.

## 4. 이 숫자를 읽을 때 주의할 것

응답 시간은 **환경에 따라 달라진다.** 위 값은 애플리케이션과 MySQL 이 같은 머신에 있는
루프백 기준이다. DB 가 네트워크 건너에 있으면 쿼리 한 번의 고정 비용이 커지므로 개선 전
쪽이 더 늘어난다. 즉 위 수치는 개선 폭의 **하한**에 가깝다.

쿼리 수는 반대로 환경과 무관하다. 그래서 두 지표를 같이 적는다. 쿼리 수는 원인을 보여주고,
응답 시간은 그 원인이 얼마짜리였는지 보여준다.

이전에는 이 수치를 H2 로 재고 "실제 MySQL 은 차이가 더 벌어진다" 고 적었는데, 실제로 재보니
그렇지 않았다. 문제집 50개 기준 H2 에서 19.3초였던 개선 전이 MySQL 에서는 10.09초로 나온다.
배수는 비슷하다. 재보지 않은 방향은 적지 않는 편이 낫다.
