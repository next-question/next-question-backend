# 생성을 작업으로 분리, 무엇을 얼마나 쟀나

문제 생성을 한 HTTP 요청 안에서 동기로 처리하던 것을 백그라운드 작업으로 떼어냈다.
이 문서는 그 개선을 숫자로 확인한 기록이다.

## 1. 두 구조의 차이

**이전, 동기 처리** (`POST member/questions/upload`)

```
업로드 → PDF 추출 → GPT 호출 → 저장 → 응답
```

GPT 응답을 기다리는 내내 톰캣 요청 스레드 하나가 묶여 있다. 사용자는 그 시간을 그대로
기다리고, 게이트웨이 타임아웃이 나면 이미 쓴 GPT 비용은 날아가고 결과도 남지 않는다.

**현재, 작업 분리** (`POST member/questions/upload/async`)

```
업로드 → PDF 추출과 검증 → 202 작업 id 응답
                              백그라운드 → GPT 호출 → 저장
```

PDF 추출과 입력 검증은 요청 스레드에서 끝낸다. 둘 다 빠르고, 잘못된 요청은 작업을 만들기
전에 알려주는 편이 낫기 때문이다. 오래 걸리는 GPT 호출만 전용 스레드 풀로 넘긴다.

기존 동기 엔드포인트는 그대로 뒀다. 이미 붙어 있는 클라이언트를 깨뜨리지 않기 위해서다.

## 2. 측정 방법

[`GenerationConcurrencyCostTest`](../../src/test/java/com/buildup/nextQuestion/performance/GenerationConcurrencyCostTest.java)
가 두 엔드포인트를 실제로 호출해서 잰다.

```bash
./gradlew test --tests "*GenerationConcurrencyCostTest"

# GPT 응답 시간을 바꿔가며 확인
./gradlew test --tests "*GenerationConcurrencyCostTest" -Dbench.gptDelayMs=10000
```

- OpenAI 자리에는 지정한 시간만큼 쉬었다가 정상 응답을 주는 로컬 스텁을 둔다.
  `openai.api.url` 이 설정값이라 코드를 건드리지 않고 바꿔 끼운다.
- 톰캣 스레드는 10개로 줄여 포화 지점을 앞당긴다. 운영 기본값은 200 이라, 같은 일이
  벌어지는 지점이 옮겨갈 뿐 구조는 같다.
- 생성 16건을 GPT 응답 시간과 같은 주기로 건다. **두 경로에 같은 속도로 걸어야 한다.**
  그냥 반복하면 즉시 돌아오는 비동기 쪽에만 훨씬 많은 요청이 들어가 비교가 성립하지 않는다.
- 단계 사이에 서버가 잡고 있던 생성이 다 빠질 때까지 기다린다. 클라이언트를 끊어도 서버는
  진행 중인 요청을 마저 처리하므로, 바로 다음 측정을 시작하면 앞 단계 부하가 섞인다.
- 재는 조회 경로는 작업 상태 조회 `GET member/questions/upload/async/{jobId}` 다.
  생성을 맡긴 사용자가 진행 상황을 보려고 실제로 부르는 경로이고, 메모리 조회라 원래는
  즉시 끝난다.

## 3. 결과

GPT 스텁 지연 10초 기준.

| | 동기(이전) | 작업 분리(현재) |
|---|---|---|
| 생성 요청 응답까지 | 10,190 ms | 12.3 ms |
| 생성 중 작업 상태 조회 p50 | 9,869 ms | 3.5 ms |
| 생성 중 작업 상태 조회 p95 | 19,894 ms | 9.3 ms |

생성이 없을 때 조회는 p50 8.3ms, p95 11.6ms 다. 즉 **작업 분리 쪽은 생성이 몰려도
무부하와 같다.**

### GPT 시간을 바꿔도 현재 값은 그대로다

| GPT 응답 | 생성 요청 응답까지 | 생성 중 조회 p50 |
|---|---|---|
| 3초 | 3,180 ms → 12.2 ms | 2,878 ms → 5.5 ms |
| 10초 | 10,190 ms → 12.3 ms | 9,869 ms → 3.5 ms |

동기 쪽은 GPT 시간을 그대로 따라간다. 작업 분리 쪽은 12ms 에서 움직이지 않는다.
사용자가 기다리는 시간이 외부 API 응답 시간과 끊어졌다는 뜻이고, 이게 이 개선의 핵심이다.

실제 생성은 스텁보다 오래 걸리므로 위 수치는 하한이다.

## 4. 안 잰 것

- **문서 분할.** 조각을 나눠도 총 입력 토큰은 줄지 않는다. 조각마다 프롬프트가 반복되니
  오히려 는다. 얻는 것은 입력 한도를 넘겨 요청이 통째로 실패하던 일이 없어진 것이라,
  시간이나 양으로 잴 값이 아니다.
- **유형별 문제 수 배분.** 이건 성능이 아니라 정확성이다. 최대 잔여법으로 합계를 요청한
  수와 맞추는 것은 `QuestionTypeDistributorTest` 가 단언한다.
- **재시도로 건진 비율.** 실제 트래픽이 있어야 의미가 있다. 지금은 어떤 실패에 다시
  보내고 어떤 실패에 즉시 포기하는지를 `GPTServiceRetryTest` 로 고정해 뒀다.

## 5. 포트폴리오에 쓸 때

3절 수치는 **GPT 스텁 지연을 반드시 같이 적는다.** 10,190ms 는 스텁 10초에서 나온 값이라
전제가 빠지면 숫자가 혼자 걸어다닌다.

가장 센 한 줄은 이것이다.

> 생성 16건이 도는 동안 작업 상태 조회가 9.9초 걸렸다. 작업으로 분리한 뒤에는 3.5ms 로,
> 생성이 없을 때와 같아졌다.

곁들일 문장은 이것이다.

> GPT 응답 시간을 3초에서 10초로 늘리면 동기 쪽은 3.2초에서 10.2초로 따라 늘지만
> 작업 분리 쪽은 12ms 에서 움직이지 않는다.
